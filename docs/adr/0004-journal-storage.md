# 0004: Segmented incremental Journal

Status: accepted design for the replacement durable format

## Facts and identities

`AgentJournal` owns mutation admission, receipt validation, reconciliation and Session restoration. One store directory has a persisted random `storeID` and one explicit `operationDomain`. Session IDs isolate conversations and run ownership; the operation domain scopes stable mutation identities across all Sessions in that store. A second directory with the same domain label has an independent ledger. The owner holds an OS exclusive lock on a stable lock file from create/open through safe close. A second process or handle is refused. Session leases and physical drain still fence the same Session within the owner process. No network filesystem, active cross-process reader, replication or online directory-copy contract is offered.

Committed user, assistant and tool messages with stable message IDs and order are formal facts. Mutation intent, state, identity binding, trusted receipt, replay output and explicit reconciliation are facts. A request projection or summary is a derived model view and does not overwrite formal messages or mint Evidence. Session recovery heads and mutation lookup files are indexes reconstructible from committed batches, but their published versions are integrity-checked before use. Diagnostic model-attempt records may be discarded after bounded retention. A terminal identity is retained while the domain exists, without TTL. Aborted means trusted confirmation of no effect, so a matching identity may enter a new lifecycle; a conflicting semantic request does not inherit that permission. No local ledger can guarantee an arbitrary external service exactly once.

## Layout and publication

A new directory contains `format.json` (magic, schema, storeID, domain), a stable `.writer.lock`, `CURRENT`, immutable `roots/`, `layouts/`, `segments/`, `sessions/`, `operations/`, `calls/`, `messages/`, `positions/`, `state/`, `blobs/`, `blob-index/`, and managed `tmp/`. Managed filenames include the persisted storeID and a generated identifier. Index envelopes also carry storeID, the full lookup key and a payload digest. Durable metadata never supplies an absolute or unchecked user path. An old framed file or an unknown nonempty directory is rejected; create and open are distinct operations. There is no legacy decoder or migrator.

A bounded, checksummed, versioned batch frame appends to an active segment. It carries a unique commit ID, logical sequence, Session revision, new formal messages and their stable IDs, steering/continuation updates, and any mutation transition. A successful mutation's receipt, replay output, terminal state and formal tool result are one frame. Large payloads are synced managed blobs referenced by a frame; references cannot publish before the blobs are durable. The frame's DTO/schema is versioned independently of public Swift enum encoding. The active segment is synced before indexes and a new immutable root are written and synced. The small `CURRENT` pointer is atomically replaced and its parent directory synced last; that is the visibility boundary. A root contains the committed segment end offset, logical sequence, layout generation and the digest of its layout; `CURRENT` contains the root digest. Index envelopes verify their own payload digests and full keys. A complete but unpublished tail is not committed and is truncated on exclusive open. A complete published frame with a bad checksum is corruption, not a disposable tail. The published root and used index/payload chain are checked; an invalid latest root does not silently roll back to an older one.

Operation and call indexes are sharded by a stable digest and verify the full original key. A per-Session head and each message ordinal point to a committed batch position. Index updates retain the previous committed pointer until the new root is reliable, so a crash before publication cannot make an unpublished index entry visible. The store lock serializes identity lookup, semantic conflict check and intent publication. A Session's expected revision is checked under that lock and changes only for that Session; an unrelated Session's commit does not invalidate it. Logical sequence and message IDs survive layout maintenance. The per-Session store revision is a storage concurrency check; `conversationSnapshot().revision` remains a process-local binding cursor and is not redefined as the store sequence. Each append writes its own delta and bounded index/root metadata. It never decodes the whole store or serializes complete history to compute a disk diff. Restoring Session A traverses A's indexed message ranges and its bounded current state, without materializing Session B or terminal mutation lifecycles. A request for the full Session may naturally read its full formal content.

The asynchronous create/open entry checks a cooperative deadline before and after the owned synchronous I/O. A synchronous disk call cannot be interrupted mid-call; the async entry waits for it to finish. The write lock is nonblocking: a competing writer receives `storeInUse`. Startup admission checks cancellation/deadline before its publication boundary. Once publication starts, the result may be committed, uncommitted or unknown; the owner retains the lock and Run responsibility until it can determine the state or fails closed. Intent uncertainty never authorizes the executor. Failure after an external effect and before settlement quarantines the operation. No database transaction or store lock spans a provider/tool call or drain wait. Actor isolation does not make synchronous I/O nonblocking; AgentJournal uses an owned serial executor on supported OS floors; file maintenance runs on a separate owned utility queue and close waits for it.

## Segments and automatic maintenance

An active segment rotates after a commit reaches the configured byte threshold; one frame is never split. Segment creation and directory sync precede publishing a root that references it. Direct indexes avoid a startup tail replay; the default policy bounds segment bytes, batches per segment, one maintenance candidate and unreclaimed sealed bytes; sustained foreground traffic schedules bounded work without requiring a Host pre-turn call. Maintenance exposes progress, latency, reclaimed bytes and errors. The initial default rotates by 2 MiB or 128 batches, bounds one pack at 4 MiB, and pauses new intent admission beyond 64 MiB of sealed work. These bounds cap foreground publication work and allow in-flight settlement to use the ordinary path; they are not a fixed disk-size promise. `Scripts/benchmark-journal.sh` measures the default against fixed-state, growing-state and unrelated-ledger fixtures and records the exact SHA in the review. If it cannot keep up, new admission fails clearly before exhausting settlement reserve; in-flight settlement retains priority.

Maintenance captures a committed boundary S and pins one already sealed segment while it builds a bounded immutable state pack. It copies all formal messages still referenced by any Session, plus current pending/terminal mutation state, receipt and output where needed. The candidate is verified against the source and synced. In the writer coordinator it rebases only the affected positions/indexes onto the *current* root, preserving commits after S; if a safe rebase is impossible, it abandons the candidate. An immutable layout generation and root are synced, then `CURRENT` is atomically published and its directory synced. This is physical maintenance, not a new logical conversation or a new mutation identity.

Only after the new root is confirmed reliable and no reader/candidate pins the old segment can GC delete that sealed segment. A segment with even one untransferred formal message or mutation fact stays. Pending, reconciliation, settled identity, trusted receipt and promised output do not expire. Large blobs stay while referenced by messages or the ledger. The active segment, lock file, unknown user files, foreign store files and symlink escapes are never GC targets. Managed temporary files and obsolete roots/index generations are collected incrementally through bounded directory cursors only after validating the current root. A failed candidate leaves the old chain intact; a published root with incomplete deletion leaves redundant files for the next bounded pass. Uncertain root publication blocks GC until recovery confirms it. No physical compaction deletes formal chat because a model context policy shortened its request view.

## Interface and failure behavior

`create(at:operationDomain:policy:)` refuses an existing path; `open(at:)` refuses a missing path, old format, future schema, invalid root or unavailable owner lock. `close()` refuses active Runs/drain and completes accepted storage work before unlocking. Hosts may inspect state and request maintenance, but do not orchestrate every rotation. Throwing, paginated message/ledger diagnostics replace nonthrowing full-record snapshots. Recovery errors never become empty history or memory fallback. An offline backup requires safe close and a complete directory copy; copying an active directory is not a supported snapshot. The supported durability tests cover process termination and injected I/O failures, not physical power loss.

PR #18 is a draft patch for a superseded framed format. Its performance report motivates this design, but the new branch does not depend on that patch, retain its compaction API, or reuse the old format. It stays open until the replacement passes the new qualification suite and is reviewable.
